DAS PROTOKOLL VERSTEHEN

ACP ist die Verbindung.
Zusammenarbeit ist die Anwendung.

Ein Editor oder eine andere Oberfläche ist der Client. Ein Coding-Agent läuft typischerweise als eigener Prozess. ACP vereinheitlicht deren Gespräch – unabhängig vom verwendeten Modell.

01 / VERBINDEN

Fähigkeiten aushandeln

Der Client startet den Agenten und sendet initialize. Beide Seiten tauschen Version und Fähigkeiten aus. Falls erforderlich, folgt eine vom Agenten angebotene Anmeldung.

02 / ARBEITEN

Eine Sitzung, viele Nachrichten

session/new legt die Sitzung an. Mit session/prompt startet ein Turn. Der Agent streamt session/update und kann Dateioperationen oder Freigaben anfordern. Die Prompt-Antwort beendet den Turn mit einem Stop-Grund.

03 / KOOPERIEREN

Ein Vermittler verbindet Aufgaben

Ein Orchestrator kann Agent A beauftragen und dessen Ergebnis an Agent B übergeben. Er verwaltet getrennte Sitzungen, Kontext und Freigaben. ACP definiert dafür keinen automatischen Peer-Kanal und keinen gemeinsamen Agentenspeicher.

Browser, Xcode, Cursor und Grok

Eine Browseroberfläche kann als Client-UI dienen. Für lokale stdio-Agenten braucht sie eine lokale Brücke, eine Erweiterung oder einen geeigneten Dienst. JavaScript in einer normalen Webseite kann keinen lokalen Agentenprozess direkt starten.

Ein Editor wie Xcode benötigt eine passende Integration. Eine Installation allein macht weder Editor noch Agent ACP-kompatibel. Cursor wird offiziell als ACP-Agent über die CLI geführt; daraus folgt keine pauschale Aussage über jede Cursor-Oberfläche. „Grok“ kann Modell, Chatprodukt oder Coding-Werkzeug bedeuten: prüfe den konkreten ACP-Endpunkt beziehungsweise Adapter.

Und A2A?

A2A wurde von Google initiiert und wird unter der Linux Foundation weitergeführt. Es beschreibt die Zusammenarbeit eigenständiger Agentendienste, unter anderem mit Agent Cards, Aufgaben und Ergebnissen. ACP-Unterstützung bedeutet keine A2A-Unterstützung. Ein Agent kann beides implementieren, oder ein Adapter übersetzt zwischen den Rollen. Auch ein Agent kann ACP-Client eines weiteren Agenten sein – diese Rolle muss die Anwendung ausdrücklich implementieren.

C4 richtig einordnen

C1 = Systemkontext, C2 = Container, C3 = Komponenten, C4 = Code. Ein C4-Container ist eine ausführbare Anwendung oder ein Datenspeicher, nicht automatisch ein Docker-Container. Der hier gewünschte Ablauf auf Ebene vier ist eine Structurizr dynamic View, ausdrücklich kein klassisches Code-Diagramm. Das Beispiel zeigt ein mögliches Anwendungsdesign, keine von ACP vorgeschriebene Architektur.
